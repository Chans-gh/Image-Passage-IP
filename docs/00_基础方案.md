## 1. 定位与范围

- **做什么**：图文内容，即「一组图片 + 一篇发布正文」。图片承载核心内容，正文补充条件、细节和经验。
- **平台**：小红书、微信贴图号。平台差异（尺寸、图片数、标题正文上限、标签）以「平台预设」的方式单独维护，规则主体不绑定某个平台。
- **形态**：
  - WorkBuddy 开放生态中的**专家**（`expertType: agent`）
  - 可直接安装到 Codex、Claude Code 等支持 Agent Skills 的环境中的**技能**
  - 公开的 GitHub 仓库
- **协议**：MIT

## 2. 已确认的决策

| # | 议题 | 决定 |
|---|---|---|
| 1 | 定位 | 图文（图片 + 正文），覆盖小红书和微信贴图号 |
| 2 | 出图方式 | 按当前模型能力分流：多模态模型直接出图；纯 LLM 用 SVG/HTML 出图；都不满足时由用户在 `.env` 里配置图片 API 和 KEY |
| 3 | 外部图片 API | 不预置任何厂商，只定一个通用调用约定，接口由用户自己选 |
| 4 | WorkBuddy 形态 | 做成「专家」，不是单独的「技能」 |
| 5 | 文件语言 | 正文用中文；frontmatter 描述中英双语 |
| 6 | 协议 | MIT |
| 7 | 角色 | 删除原作者的角色图；保留「用户自带角色」功能（可选），并提供角色资产的提示词模板 |
| 8 | 专家形态 | 单个 agent；流程和规则都放在 skill 里，agent 文件只写人设和入口 |
| 9 | SVG 渲染依赖 | Node 和 Python 两条实现都可以接受 |

## 3. 逻辑链路：输入 → 运作 → 输出

```
【输入】
 ├─ 当次请求：主题 / 读者与收获 / 场景 / 范围 / 页数·画幅·字数 / 平台
 ├─ 账号长期配置（profile.md）：定位、口吻、主色、人物模式、默认平台
 ├─ 已有状态（state.json）：已确认的策划版本、采用的 P1、已完成页、授权范围、渲染模式
 ├─ 素材：照片 / 截图 / 经历 / 测试记录 / 来源
 └─ 角色资产（可选）：用户上传或用模板生成的角色参考图

【运作】
 ① 解析有效配置：逐字段按「当次 ＞ 本次已确认 ＞ 账号长期 ＞ 项目默认」取值
 ② 解析渲染模式：native / svg / api（见第 5 节）
 ③ 判断阶段与范围：查授权表，决定从哪个节点继续、要不要等确认
 ④ 内容价值与核实：一个场景、一个问题、一个观点；公开信息去查，私有经历不编
 ⑤ 选型：T 内容模板 → V 视觉风格（结合渲染模式的适配度）→ 每页 L 版式 → 页数
 ⑥ 完整策划 ──▶【确认节点 1】
 ⑦ 生成 P1 ──▶【确认节点 2】→ 锁定风格参数
 ⑧ 逐页循环：只提取当前页 → 独立生成 → 立即质检 → 修正或重做 → 记录采用版本
 ⑨ 发布文案：按平台预设和主模板出标题、正文和标签
 ⑩ 发布前复核：如实报告完成、待修、待补的部分

【输出】
 策划文档 · P1 · N 张独立单页（PNG）· 标题 + 正文 + 标签 + 来源/日期 · 状态报告
 （全部写入工作区，换会话可以接着做）
```

## 4. 分发：一套规则，三个运行环境

```
同一个仓库
├─ WorkBuddy：.codebuddy-plugin/plugin.json + agents/*.md 作为「专家」上架，预加载 skills/
├─ Codex：直接安装 skills/image-passage/
└─ Claude Code：直接安装 skills/image-passage/
```

- 在 Codex 和 Claude Code 里没有 agent 这层包装，所以 **skill 必须单独就能完整工作**。
- SKILL.md 的头部同时写两套字段：`name / description`（Codex、Claude Code）和 `title / summary / read_when`（WorkBuddy 模板）。

### WorkBuddy 规范中需要注意的约束

| 规范 | 处理方式 |
|---|---|
| agent 文件不能声明 `tools`，权限由系统分配 | 不写 `tools`。依赖的 Bash、Read、Write、WebSearch、WebFetch 都在内置工具里 |
| 包内不能写真实的 key 或 token | 只提供 `.env.example`；`.env` 放在用户工作目录，并加入 `.gitignore` |
| 中文 `displayDescription` 要 40～50 字 | 草案 44 字（见 9.1） |
| `defaultInitPrompt` 必须等于 `quickPrompts` 的第一项 | 草案已对齐 |
| `tags`、`quickPrompts` 各恰好 3 个 | 草案已对齐 |
| 头像要求 512×512 PNG，≤500KB，放在 `avatars/` | 待作者提供（不能使用原角色 IP） |
| `categoryId` | `06-ContentCreative` |

## 5. 出图分流（render routing）

```
解析渲染模式
 ├─ .env 里显式写了 RENDER_MODE=native/svg/api ─▶ 照写的执行（最高优先级）
 └─ RENDER_MODE=auto（默认）：
     ① 当前环境有原生生图工具（如 Codex 生图、WorkBuddy Hy4）   ─▶ native：直接出图
     ② 没有生图工具，但模型能写代码（如 Opus、DeepSeek）          ─▶ svg：SVG/HTML 排版 → 渲染成 PNG
     ③ 以上都不满足                                               ─▶ api：读 .env 调用图片接口
                                                                    没配置时提示用户补接口和 KEY，不硬出图
```

**判断原则**：按「当前环境里有没有生图工具」判断，不按模型名判断。模型很难可靠地知道自己是谁，换名、套壳都会让名单失效。模型名单只作为辅助参考。

渲染模式确定后写入 `state.json`，同一套图中途不换模式。确实需要换时，按「改变主风格」处理，重新确认 P1。

### 5.1 风格 × 渲染路线适配（待细化）

SVG 路线和 10 类风格不是一一对等的，需要在策划阶段告诉用户哪些风格会降级。初步判断如下：

| 风格 | native / api | svg | 说明 |
|---|---|---|---|
| V01 彩铅手绘 | 完整 | 简化 | 可用滤镜模拟纸纹和笔触，但做不出真实彩铅质感 |
| V02 商业情报手稿 | 完整 | 适合 | 以排版、数字、细线为主 |
| V03 极简信息卡 | 完整 | 很适合 | 本质是排版 |
| V04 生活方式杂志 | 完整 | 依赖素材 | 需要用户提供照片；没有大图时会退化成字排 |
| V05 手账拼贴 | 完整 | 依赖素材 | 照片和票据由用户提供，装饰可用 SVG 绘制 |
| V06 实拍/截图批注 | 依赖素材 | 很适合 | 真实截图直接嵌入，批注精确，保真性最好 |
| V07 扁平插画科普 | 完整 | 简化 | 几何图形可以画，复杂场景插画能力有限 |
| V08 情境漫画/对话 | 完整 | 简化 | 人物需要嵌入角色资产 PNG（见第 6 节） |
| V09 图鉴/档案页 | 完整 | 适合 | 对象图片由用户提供或用简化图标 |
| V10 书页/阅读批注 | 完整 | 很适合 | 本质是排版 |

反过来，native 和 api 两条路线的主要风险是**中文文字渲染**，需要在 `prompt-recipes.md` 里规定上图文字的长度、数量和质检方式。

### 5.2 `.env.example` 草案

```bash
# 渲染模式：auto | native | svg | api
RENDER_MODE=auto

# 仅 api 模式需要；默认按 OpenAI 兼容的 /images/generations 格式调用
IMAGE_API_BASE_URL=
IMAGE_API_KEY=
IMAGE_API_MODEL=
# 可选：参考图（P1、角色资产）的传递方式，接口不支持就留空
IMAGE_API_REFERENCE_MODE=

# 输出规格（平台预设可覆盖）
OUTPUT_WIDTH=1242
OUTPUT_HEIGHT=1656
```

## 6. 角色资产（可选功能）

### 6.1 功能边界

- **默认不启用**。没有配置角色时，整套图不出现账号角色。
- 角色只服务于叙事：辅助操作、观察、批注、对话。出现在哪些页、出现几次由内容决定，没有固定配额。
- **账号角色**和**剧情人物**分开：剧情人物是漫画或演示里的一次性角色，不自动视为账号角色。
- 只上传了角色图不等于启用，需要在 `profile.md` 或当次请求里明确启用。
- 角色资产只建一次，之后跨项目反复使用。

### 6.2 人物模式（替代 V3.1 的三种 IP 模式）

| 模式 | 说明 |
|---|---|
| 不使用账号角色 | 默认 |
| 使用用户上传的角色参考图 | 用户自备图片，Skill 根据图片整理出识别特征卡 |
| 先生成角色资产，再使用 | 用第 6.4 节的模板生成一套角色资产，用户确认后存档 |

### 6.3 角色资产包

存放位置：`image-passage-work/_assets/characters/<角色名>/`

| 文件 | 内容 | 用途 |
|---|---|---|
| `character.md` | 识别特征卡：名字、定位、发型发色、服装、主色 HEX、头身比、配饰、**不可改变项**、可变项 | 所有渲染模式都要读取，写进每页的提示词 |
| `sheet.png` | 设定图：正面、侧面、背面全身三视图 | native / api 的主参考图 |
| `expressions.png` | 表情组 | 按页面情绪选用 |
| `poses/*.png` | 常用动作单图，**透明背景** | svg 模式直接嵌入；native / api 也可作为参考 |

SVG 模式下，LLM 画不出一致的角色，因此角色只能**嵌入现成的透明背景 PNG**。这也是动作单图要做成透明背景的原因。

### 6.4 角色设定图提示词模板（初稿）

```text
【角色设定图｜Character Reference Sheet】

用途：为图文账号建立一个可反复使用的固定角色，本图只用作参考，不用于发布。

角色定位：{一句话，例如：陪读者整理工作方法的职场伙伴}
画风：{例如：扁平插画 / 彩铅手绘 / 日系简笔 / 3D 软萌}，与账号主风格 {V 编号} 协调
外观：
- 年龄感与体型：{例如：成年，三头身 Q 版 / 七头身写实}
- 发型与发色：{ }
- 服装：{上装、下装、鞋}，主色 {HEX}，辅助色 {HEX}
- 识别特征：{例如：圆框眼镜、胸前徽章、固定发夹}（2～3 个，全图保持一致）
构图：
- 同一张横版画布，纯白或浅灰纯色背景
- 同一角色的正面、侧面、背面全身三视图，并排，大小一致，脚底对齐
- 无文字、无水印、无场景、无其他人物
要求：三个视角的发型、服装、配色、比例和识别特征完全一致；线条干净，便于后续参考。
```

```text
【表情组｜Expression Sheet】

参考：上一张角色设定图，保持外观完全一致。
内容：同一角色的头部或半身，{6} 种表情排成 2×3 网格：
{开心 / 认真思考 / 惊讶 / 无奈 / 鼓励 / 专注}
背景：纯白；无文字、无水印。
```

```text
【动作单图｜Pose】

参考：角色设定图，保持外观完全一致。
动作：{例如：一手指向右侧 / 双手举着空白牌子 / 低头看手机 / 拿笔记录 / 托腮思考 / 比 OK}
构图：单个角色全身，居中，四周留白；透明背景（接口不支持时用纯白背景，后期抠图）。
无文字、无道具上的字、无水印。
```

> 这三个模板都是「生成资产」用，属于一次性的准备工作，不受「一页一图」规则约束。表情组的网格是资产图的内部结构，不是多页拼版。

### 6.5 角色的真实性与权利边界

- 用户上传的角色图需由用户自己拥有使用权。
- 不仿制知名 IP 或现有动漫、品牌角色；不在未经同意的情况下生成真实人物的肖像。
- 角色是创作者的形象代言，不等于「创作者本人亲测」。第一人称经历仍需真实依据。

## 7. 状态与工作区

ChatGPT 项目靠对话记忆完成「内部记录」；Agent 会话是短暂的，所以把状态落成文件：

```
image-passage-work/
├── profile.md                 # 账号长期配置（跨项目）
├── _assets/characters/...     # 角色资产（跨项目，可选）
└── <项目名>/
    ├── plan.md                # 策划，带版本号
    ├── state.json             # 渲染模式、有效配置、确认/授权记录、P1、各页状态与采用版本
    ├── pages/                 # P01.png … PNN.png（svg 模式另存 .svg/.html 源文件）
    └── copy.md                # 标题、正文、标签、来源
```
