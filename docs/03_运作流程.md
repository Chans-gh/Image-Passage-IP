# 运作流程：初始化、输入与出图（草案）

状态：讨论稿，尚未开发
整理日期：2026-10-29
前置文件：[00_基础方案.md](00_基础方案.md)、[02_变量核查与扩充.md](02_变量核查与扩充.md)

本文件回答三个问题：

1. 首次使用时，用户可以补充哪些个性化配置，每一项影响后面哪个环节。
2. 用户可以用哪些形式给输入，怎样兼容多种形式和组合。
3. 出图怎么做：ChatGPT 网页版里是黑盒，在 Skill 里要怎样运作。

---

## 0. 总流程

```
安装
 └─ 首次使用 ──▶【初始化，可跳过】──▶ profile.md（账号长期配置）
                                        │
每次创作                                 ▼
 输入（任意形式与组合）
  └─▶ ① 输入归一化：每份素材判断用途和可信度 ──▶ inputs.md
  └─▶ ② 解析有效配置：当次 ＞ 本次已确认 ＞ profile.md ＞ 项目默认
  └─▶ ③ 解析出图能力：能不能生图 × 能不能看图 ──▶ 渲染路线（第 3 节）
  └─▶ ④ 判断范围：完整套图 / 只策划 / 只文案 / 改某页 / 继续上次
  └─▶ ⑤ 内容价值与核实
  └─▶ ⑥ 选型与完整策划 ──▶【确认节点 1】
  └─▶ ⑦ P1 封面 ──▶【确认节点 2】──▶ 锁定风格（style-lock.md）
  └─▶ ⑧ 逐页：页面规格单 → 编译 → 生成 → 质检 → 修正 → 采用
  └─▶ ⑨ 发布文案
  └─▶ ⑩ 发布前复核与状态报告
  └─▶（可选）把本次的选择存为账号默认 ──▶ 回写 profile.md
```

相比 [00_基础方案.md](00_基础方案.md) 第 3 节，新增了三处：开头的**初始化**、①的**输入归一化**、③从「有没有生图工具」细化为**两项能力**。

## 1. 首次初始化与个性化配置

### 1.1 原则

- **全部可选**。不做初始化也能直接开始创作，一句话就能出一套图。
- **不挡路**。首次使用时提供四个选项，用户选「跳过」就直接进入创作。
- **边用边存**。每次创作结束，询问一次「是否把这次的选择（口吻、风格、主色……）存为账号默认」。这样不做初始化，用几次之后 profile 也会慢慢补齐。
- **可以随时修改**。用户说「更新账号配置」「以后都用 K3 口吻」就改写 profile.md。
- **存放在用户工作区**，不放在 skill 目录里。skill 升级或重装不会覆盖用户配置。
- **每项都标来源**：用户填写 / 从内容提取 / 系统默认。提取得到的值在用户确认前不当作定论。

### 1.2 四种初始化方式

| 方式 | 用时 | 过程 |
|---|---|---|
| 跳过 | 0 | 直接开始创作。所有字段使用项目默认，或按当次主题推断 |
| 快速设置 | 约 1 分钟 | 只问 5 个 ★ 项（见 1.3），一次问完，不追问 |
| 完整设置 | 约 5～10 分钟 | 按 1.3 的 A～H 组逐组填写，每组都可以跳过 |
| 从已有内容提取 | 约 2 分钟 | 用户提供自己过往 3～9 篇笔记的截图（图片和正文）或主页截图。Skill 提取定位、读者、口吻、风格、主色、字体，生成 profile 草稿，用户确认后保存 |

「从已有内容提取」最省事，效果也最好，因为提取的是用户真实的风格。限制是：提取视觉风格需要模型能看图，纯文本模型只能从正文里提取定位和口吻。

### 1.3 配置项与影响

★ 表示快速设置的 5 个问题。

**A. 账号定位**

| 配置项 | 不填时 | 影响哪里 |
|---|---|---|
| ★ 发布平台：小红书 / 微信贴图号 / 两者 | 按当次请求判断；没说明时用小红书预设 | 平台预设：图片数上限、标题和正文上限、标签规则 → 篇幅 F 的上限、⑨ 文案 |
| ★ 一句话定位＋主要领域（D） | 每次按主题单独判断 | 选题建议、读者价值 R 的优先级、模板 T 的倾向、钩子 H、正文切入角度；保证账号内容的一致性 |
| ★ 目标读者：身份、阶段、常见困扰 | 按主题推断 | R、H、字数档 S、口吻 K、术语深浅、举例场景 |

**B. 创作者**

| 配置项 | 不填时 | 影响哪里 |
|---|---|---|
| 身份与可公开的资历 | 不提身份 | 第一人称的可信度、写法 W（经验类）、合规（不冒充医生、律师、理财师等资质） |
| 亲历范围：真正做过、用过、去过的 | 不写第一人称亲测 | ⑤ 核实：哪些内容能写成「我试过」；没有依据时只用「整理 / 分析」口径 |
| 内容边界：不碰的话题、品牌，商业合作的标注方式 | 按通用合规规则 | 选题筛选、合规检查、⑩ 复核 |

**C. 口吻**

| 配置项 | 不填时 | 影响哪里 |
|---|---|---|
| ★ 口吻预设 K1～K6 | 按模板 T 推荐 | ⑨ 标题和正文、上图短文案、封面主文案 |
| 称呼读者的方式、常用表达、禁用词、emoji 习惯 | 不使用固定称呼和口头禅 | 文案细节；禁用词进入 `check_copy` 自动检查 |

**D. 视觉**

| 配置项 | 不填时 | 影响哪里 |
|---|---|---|
| ★ 偏好风格 V（1～3 个）、不用的风格 | 按内容和渲染路线推荐 | ⑥ 风格选型。偏好只是优先，内容不适合时仍会说明并换风格 |
| ★ 主色、辅助色（颜色名） | 按风格推荐 | 风格参数「色彩」、HEX 推导、P1 |
| 字体倾向：手写 / 黑体 / 宋体 / 圆体 | 按风格推荐 | 风格参数「字体」；svg 和叠字时选用的具体字体 |
| 风格参考图：最好是自己过往的笔记 | 无 | P1 生成时作为参考图；提取风格参数。他人作品只提取参数，不复制构图和内容 |

**E. 品牌元素**

| 配置项 | 不填时 | 影响哪里 |
|---|---|---|
| 署名 / 水印：文字、位置、出现在哪些页 | 不加 | 每页版式预留位置；风格参数「组件」 |
| 固定结尾：末页固定引导语、正文固定结尾 | 按体裁生成收束 | 末页设计、⑨ 正文结尾 |
| 固定标签 | 每次按内容生成 | ⑨ 标签：固定标签＋内容标签 |

**F. 人物**

| 配置项 | 不填时 | 影响哪里 |
|---|---|---|
| 人物模式、角色资产（见 00 第 6 节） | 不使用账号角色 | 每页的人物安排、提示词和参考图、svg 模式嵌入角色 PNG、V08 情境漫画是否可选 |

**G. 工作习惯**

| 配置项 | 不填时 | 影响哪里 |
|---|---|---|
| 默认篇幅 F1～F5 | 按内容判断 | 页数 |
| 确认节点：每次都确认 / 策划确认后连续出图 / 全部免确认 | 每次都确认 | ⑥⑦ 是否停下等待 |
| 双图笔记是否显示页码 | 不显示 | 页码组件 |
| 是否在对话里展示提示词 | 不展示（文件里始终保存，见 3.10） | 输出内容 |
| 每页最多重试次数 | 2 次 | ⑧ 失败后何时停下，记为待处理 |

**H. 素材库**

| 配置项 | 不填时 | 影响哪里 |
|---|---|---|
| 常用素材目录：产品图、个人照片、常用截图 | 每次单独提供 | 素材是否够用 → V04 杂志、V05 手账、V06 实拍批注、V09 图鉴能不能选 |

**技术配置**（写在 `.env`，不写进 profile）

| 配置项 | 不填时 | 影响哪里 |
|---|---|---|
| `RENDER_MODE`、图片 API | 自动判断 | ③ 渲染路线 |
| 语音转写 API（可选，见 2.3） | 音频和视频需要用户提供文字稿 | 音频、视频输入 |

## 2. 输入：形式和组合

### 2.1 原则

- **一句话就能开工**。素材越真实、越完整，成品上限越高，但不要求一次给齐。
- **形式不等于用途**。同样是一张图片，可能是要放进页面的实拍素材，也可能只是风格参考。所以先判断每份输入的**用途**，再决定怎么用。
- **先归一化，再创作**。所有输入先整理成一份素材清单 `inputs.md`。后续策划、出图、文案都只读这份清单和 `inputs/` 里的原文件，不反复回看聊天记录。换会话也能接着做。
- **能力不够时如实说明**。当前环境处理不了某种输入（例如纯文本模型看不了图片），就说清楚缺什么、可以怎么补，不假装读过。

### 2.2 输入形式

| # | 形式 | 例子 | 处理方式 | 环境处理不了时 |
|---|---|---|---|---|
| 1 | 一句话 | 「写一篇新手养绿萝」 | 判断主题 D，推断读者和价值 | — |
| 2 | 一段话 / 口述稿 | 一段经历、想法、清单草稿 | 拆出事实、观点、经历和情绪 | — |
| 3 | 文档 | md、txt、docx、pdf、pptx | 用脚本提取文字和内嵌图片 | 请用户粘贴正文 |
| 4 | 表格 / 数据 | xlsx、csv、测试记录 | 读取数据，供表格、对比、图表类版式使用 | 请用户粘贴关键数据 |
| 5 | 实拍照片 | 产品、场景、过程、前后对比 | 看图描述内容；判断能否作为上图素材 | 纯文本模型：请用户每张写一句说明。图片仍然可以嵌入页面 |
| 6 | 截图 | App 界面、网页、聊天、数据后台 | 读出文字和数字；检查隐私信息 | 纯文本模型：用 OCR（tesseract 中文包）提取文字；没有 OCR 时请用户说明 |
| 7 | 手写 / 手绘稿 | 草图、笔记、思维导图 | 识别结构，转成策划草稿 | 请用户口述 |
| 8 | 参考图 | 喜欢的笔记、风格样例 | 只提取风格参数，不复制构图和内容 | 纯文本模型：请用户用文字描述风格 |
| 9 | 角色图 | 自己的角色形象 | 进入角色资产流程（00 第 6 节） | 纯文本模型：请用户填写特征卡 |
| 10 | 网页 / 文章链接 | 官网、新闻、公众号文章 | 抓取正文，记录来源和日期 | 抓取失败（需要登录、防爬）：请用户粘贴正文或截图 |
| 11 | 笔记链接 | 小红书、微信贴图笔记 | 通常需要登录，大多抓不到 | 请用户提供截图。他人笔记只作参考 |
| 12 | 视频链接 | B 站、抖音、视频号 | 只能拿到标题和简介 | 请用户提供文字稿或视频文件 |
| 13 | 音频 | 语音备忘、播客片段 | 转写成文字稿 → 按第 2 项处理 | 没有转写能力：请用户用手机自带转文字后粘贴 |
| 14 | 视频文件 | vlog、录屏、开箱 | 抽音轨转写＋抽关键帧。关键帧可作为上图素材 | 没有 ffmpeg：请用户截几张关键画面＋提供文字稿 |
| 15 | 已有成稿 | 自己的公众号长文、旧笔记 | 改写为图文：压缩、拆页、换结构 | — |
| 16 | 已有项目 | 「继续上次那套」「把第 3 页改一下」 | 读取 state.json，从未完成的节点继续 | — |

### 2.3 音频和视频

主流 Agent 环境大多不能直接「听」音频。建议分三档处理：

1. 环境本身能理解音频：直接用。
2. 用户在 `.env` 里配置了语音转写 API（可选，OpenAI 兼容格式）：调用转写。
3. 都没有：请用户用手机或会议软件自带的转文字功能，粘贴文字稿。

视频 = 音轨 ＋ 画面。音轨按上面三档处理；画面用 ffmpeg 按场景变化抽 6～12 张关键帧，拼成一张预览图给模型看，选出可用画面作为上图素材（常用于 V06 实拍批注）。

```bash
# .env.example 中追加（可选）
TRANSCRIBE_API_BASE_URL=
TRANSCRIBE_API_KEY=
TRANSCRIBE_API_MODEL=
```

### 2.4 素材用途

归一化时，每份输入标出一个或多个用途：

| 代号 | 用途 | 喂给哪里 |
|---|---|---|
| S | 选题线索 | 主题 D、读者价值 R |
| F | 事实来源 | 核实、来源条、正文里的来源与日期 |
| X | 亲历素材 | 第一人称写法、经验类模板、可信度 |
| A | 上图素材：要放进页面的照片、截图、关键帧 | 风格 V 和版式 L 是否可选、每页素材安排 |
| Y | 风格参考 | 风格参数、P1 参考图 |
| C | 角色参考 | 角色资产 |
| K | 约束：页数、平台、必须包含的内容 | 有效配置 |
| M | 修改指令：针对某页、某处 | 修改流程 |

用途不明确、又会影响结果时，才问一句。例如用户发来一张别人的笔记截图，没有说明用途，默认按 Y（风格参考）处理，不当作上图素材。

每条素材同时标出**可信度**，沿用 V3.1 的分类：已确认事实 / 个人经验 / 分析建议 / 待观察 / 演示示例。

### 2.5 组合与冲突

**常见组合**

| 组合 | 通常走向 |
|---|---|
| 一句话 | 公开资料整理：T 知识科普、清单类；风格以排版型为主 |
| 一句话 ＋ 9 张照片 | 分享记录 T16、种草 T17；V04 杂志、V05 手账 |
| 一段语音 ＋ 几张截图 | 经验分享、教程；V06 实拍批注 |
| 一个表格 | 测评、对比；表格和数据类版式 |
| 一条公众号链接 | 改写已有成稿：压缩成 F2～F4 |
| 一份 PDF 报告 | 资讯解读、要点提炼；需要标来源和日期 |
| 风格参考图 ＋ 一句话 | 先提取风格参数，再按主题策划 |

**冲突处理**

| 冲突 | 处理 |
|---|---|
| 当次指令和 profile 不同 | 当次优先，只对本次生效；结束时问是否更新默认 |
| 用户的说法和素材不一致（说 5 项，截图里有 6 项） | 指出差异，请用户确认，不悄悄选一个 |
| 素材和公开资料不一致 | 两个都列出来，标明来源和日期，由用户决定 |
| 素材不够撑起所选风格（选了 V04 杂志，但只有 1 张照片） | 说明缺口，给两个方案：补素材，或换风格 |

### 2.6 权利与隐私

- **截图打码**：手机号、真实姓名、订单号、地址、他人头像和昵称，嵌入页面前打码。这一项加入质检清单。
- **他人肖像**：照片里出现可识别的他人面孔，提醒用户确认是否获得同意，或者模糊处理。
- **他人内容**：他人的文章、笔记只转述要点并标注来源，不整段搬运；他人的图片不作为上图素材，除非用户确认有权使用。

## 3. 出图：从黑盒到白盒

### 3.1 ChatGPT 网页版里发生了什么

在 ChatGPT 项目里，你没有写提示词，但提示词其实存在：聊天模型读完项目文件和整段对话后，**自己在内部写了一段生图指令**，再交给内置的 ImageGen。图像模型看到的是这段你看不到的指令，以及对话里的图片。

所以 V3.1 能用，靠的是两件事：

1. 聊天模型「记得」全部上下文：规则、策划、已采用的 P1。
2. 它把上下文压缩成生图指令的过程不可见，好坏只能从结果反推。

这也解释了 V3.1 里那些补丁规则的来由。例如「不要多页拼版」「其他页的内容不能作为画面输入」，本质上是在约束那段看不见的指令里不要混进别的页面。

### 3.2 Skill 里为什么要显式化

Agent 环境里的生图方式不一样：

- 生图工具（Codex 的生图、WorkBuddy 的 Hy4、外部 API）**只看到传给它的那段文字和参考图**，看不到对话、规则文件和策划。
- 不同环境、不同模型的能力差别很大，没有统一的「黑盒」可以依赖。

所以 Skill 要把 ChatGPT 内部那一步**显式化**：由 Skill 按固定结构，把「这一页需要的全部信息」写成一份文件，再交给出图环节。

这样做有五个好处：

| 好处 | 说明 |
|---|---|
| 信息隔离 | 生图工具只能看到当前页的规格单，从结构上杜绝多页拼版，不再靠反复提醒 |
| 风格一致 | 锁定的风格描述逐字写进每一页，参考图每次都带上 |
| 可复现、可排查 | 某页出错，打开它的提示词就知道问题出在指令还是模型 |
| 可修改 | 用户可以直接改某页的提示词重新生成 |
| 跨路线通用 | 同一份规格单可以编译成生图提示词，也可以编译成 SVG / HTML |

用户体验可以和 ChatGPT 一样：默认不在对话里展示提示词，用户只看到图。提示词保存在文件里，需要时再看（见 3.10）。

### 3.3 路线判断：两项能力

[00_基础方案.md](00_基础方案.md) 第 5 节只按「有没有生图工具」判断。实际上还要看**模型能不能看图**，因为它决定了能不能看懂用户的照片，以及能不能检查自己生成的图。

| | 能看图 | 不能看图 |
|---|---|---|
| **能生图** | ① 例：Codex 用 GPT、WorkBuddy 用 Hy4（待实测）。完整闭环：生成 → 看图质检 → 修正 | ② 少见。能生成，但无法自己检查，需要 OCR 或用户检查 |
| **不能生图** | ③ 例：Claude Code 用 Opus（能看图、不能生图）。svg 路线，渲染后可以看图质检 | ④ 例：DeepSeek 的文本模型。svg 路线，只能用脚本检查；用户的照片需要附文字说明 |

注意：Opus 属于第 ③ 类，它能看懂用户的照片和截图，也能检查渲染结果，只是不能生图。

任何一类在 `.env` 配置了图片 API 后，都可以用 api 路线生成画面；质检能力仍然取决于模型能不能看图。

### 3.4 单一来源：页面规格单

每一页先写一份**页面规格单**（`pages/P03/spec.md`），再按路线编译：

```
plan.md（整套策划）＋ style-lock.md（锁定风格）＋ inputs.md（素材）
              │  只提取当前页
              ▼
     pages/P03/spec.md  页面规格单（与路线无关）
              │
   ┌──────────┼──────────────┐
   ▼          ▼              ▼
 生图提示词    生图提示词      HTML / SVG
 （native）   （api）        （svg）
   │          │              │
   ▼          ▼              ▼
 原生生图工具  call_image_api  render 脚本
   └──────────┴──────┬───────┘
                     ▼
            pages/P03/v1.png → 质检 → 采用
```

**规格单的内容**（与 V3.1 母提示词第五节的每页策划对应）：

| 字段 | 内容 |
|---|---|
| 页码 | 3 / 8；是否显示 |
| 页面角色 | 封面 / 问题 / 步骤 / 对比 / 收束…… |
| 构成方式 | 整图生成 / 底图＋叠加 / 纯排版（见 3.5） |
| 版式 | L 编号；区域划分、比例、阅读顺序 |
| 上图文字 | 逐字列出，每条标层级：主标题 / 副标题 / 正文 / 注释 / 数字 |
| 焦点 | 本页要强调什么、怎么强调 |
| 素材 | 引用 inputs 中的编号；放在哪里；保真还是风格化 |
| 人物 | 不出现 / 角色名＋动作＋位置＋大小 |
| 表达元素 | E 编号：箭头、圈注、卡片…… |
| 来源条 | 有 / 无；内容 |
| 禁止项 | 本页特有的禁止项 |

### 3.5 页面构成方式（新增，待确认）

中文文字是生图模型的主要短板：字少时大多能写对，字一多就容易出错别字、乱码、漏字。真实截图交给生图模型重画，里面的数字和文字也可能被改掉，违反 V3.1「真实素材保真」的要求。

所以建议每一页单独决定**画面和文字分别由谁来做**：

| 构成方式 | 画面 | 文字 | 适合 |
|---|---|---|---|
| **G 整图生成** | 生图模型 | 生图模型 | 字少、以画面为主的页：封面、插画页、漫画页 |
| **H 底图＋叠加** | 生图模型画底图，并按版式留出空白区 | 代码叠加准确的文字；真实截图、照片按原样嵌入 | 字多的内页、表格、步骤、带截图的页 |
| **S 纯排版** | 代码排版（HTML / SVG） | 代码 | svg 路线的全部页面；本身就是排版的风格（V03、V10、V11、V12） |

**自动选择规则（初稿）**：

1. svg 路线：全部用 S。
2. 页面里有需要保真的截图或数据：用 H（截图原样嵌入，模型只画周围的装饰）。
3. 上图文字超过阈值（暂定：正文超过 30 字，或超过 4 条要点）：用 H。
4. 其余情况：用 G。
5. 同一套图里 G 和 H 可以混用，但字体必须统一。所以用了 H 的套图，G 页上的字体要按 H 的字体来描述，或者 G 页的标题也改为叠加。

**限制**：H 需要环境能运行脚本（Codex、Claude Code 可以；WorkBuddy 待实测），并且需要中文字体。字体只用开源可商用的（例如思源黑体、思源宋体、霞鹜文楷，均为 SIL OFL 协议），由脚本按需下载，不放进仓库。

### 3.6 风格锁

P1 采用后，把第 02 文件 4.2 节的 13 项风格参数写进 `style-lock.md`，分两部分：

- **描述版**：一段固定的文字，例如「暖米白纸张底，轻纸纹；鼠尾草绿为主色，炭灰文字；标题为圆润粗黑体；2px 炭灰细线描边，12px 圆角卡片……」。native 和 api 路线**逐字**放进每一页的提示词，不允许每页改写。
- **精确版**：HEX、字体名、字号、边距、线宽，写成 CSS 变量。svg 路线和 H 构成方式的文字层直接使用。

两部分来自同一组参数，所以 G、H、S 三种页面看起来是同一套。

### 3.7 提示词结构

native 和 api 路线由规格单编译成提示词，分 8 层，顺序固定：

```text
【1 画布】竖版 3:4，1242×1656。一张完整、独立的单页。不要拼版，不要出现其他页面或缩略图。

【2 风格】（逐字粘贴 style-lock.md 描述版）

【3 版式】L07 上图下文。上部 55%：……；下部 45%：……。阅读顺序：标题 → 图 → 三条要点。

【4 文字】只出现以下文字，逐字使用，不增、不改、不翻译：
  主标题：「三步救回黄叶绿萝」（最大、最粗）
  要点 1：「剪掉黄叶」
  要点 2：「换疏松土」
  要点 3：「放散射光处」
  页码：右下角「3 / 8」
  （构成方式为 H 时，本层改为：「以下区域保持留白、不画任何文字：……」）

【5 素材】参考图 #2 是用户实拍，保持主体和构图不变，只加手账胶带边框。

【6 人物】不出现。
  （启用角色时：角色「小禾」见参考图 #3，外观以特征卡为准；动作：指向右侧要点；位置：左下角；约占画面 1/5。）

【7 禁止】水印、乱码、多余文字、其他页的内容、伪造的真实界面记录。

【8 参考图说明】#1 P1 封面：只参考风格，不复制构图和文字。#2 用户实拍。#3 角色设定图。
```

提示词用中文还是中英双语、各层的措辞，需要分别在各环境实测后确定，写进 `prompt-recipes.md`。

### 3.8 参考图

每页随提示词附带的参考图：

| 参考图 | 何时带 | 作用 |
|---|---|---|
| P1 封面 | P2 起每页 | 风格锚点 |
| 首张内页 | P3 起每页 | 内页锚点：正文、卡片、表格的样式（双锚点） |
| 角色设定图 / 动作图 | 本页有角色时 | 角色一致性 |
| 本页素材 | 本页引用了素材时 | 照片、截图 |

如果生图工具不支持参考图输入，只能依靠风格锁的描述版来保持一致。这时一致性会明显变弱，建议改用更多 H 页（文字层由代码保证一致），并在策划阶段告诉用户。

同一套图里锁定生图参数：工具、模型、尺寸、质量档，以及 seed（如果支持），写入 `state.json`。

### 3.9 单页流水线与质检

```
spec.md → 编译 → 生成 v1.png → 质检 → 通过：记为采用
                                  └ 不通过：修正 → v2.png → 质检
                                    超过重试上限：记为待处理，继续其他页，最后报告
```

**质检方式取决于 3.3 的能力分类**：

| 能力 | 质检方式 |
|---|---|
| 能看图（① ③） | 模型看图，按页面级质检清单逐项检查：结构、文字、数字、素材、人物、风格、页码 |
| 不能看图（② ④） | 脚本检查：S / H 页检查文字是否溢出、字号是否达到下限、边距、对比度；G 页用 OCR 把图上文字和规格单逐字比对 |
| 无法检查的部分 | 在状态报告里如实写「未经视觉检查」，请用户抽查，不标为通过 |

**修改**：

| 构成方式 | 改文字 | 改画面 |
|---|---|---|
| G | 工具支持局部编辑就编辑；否则改提示词重生成 | 同左 |
| H | 只重新叠字，几秒完成，不动底图 | 重生成底图，文字层不变 |
| S | 直接改源文件 | 直接改源文件 |

H 页改错字几乎没有成本，这是 H 的另一个好处。

```
<项目名>/

├── inputs.md               # 素材清单（2.7）
├── plan.md
├── style-lock.md           # 风格锁：描述版 ＋ 精确版

├── pages/
│   └── P03/
│       ├── spec.md         # 页面规格单
│       ├── prompt.md       # native / api 的提示词（G、H 页）

```

- 默认在对话里只展示图片和简短说明。
- 用户说「看一下 P3 的提示词」「把 P3 的提示词里……改成……再出一次」时，展示或修改对应文件。
- profile 里「展示提示词：是」时，每页生成后附上提示词。
